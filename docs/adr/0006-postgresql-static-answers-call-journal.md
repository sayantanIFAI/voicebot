# ADR 0006 — PostgreSQL for the clinic API; static answers loaded once a day; the call log as one record per call

**Status:** Accepted, live on the pilot pod (git `main`). Extends [ADR 0005](0005-capacity-round-2026-10-29.md), whose last open item (a server database) this closes.
**Date:** 2026-10-29
**Driver:** the owner asked for (1) a free, commercially usable server database in place of SQLite, (2) test prices / preparation / FAQ answers served from memory and loaded once a day, (3) the call log written as one record per call and archived by a nightly batch.

## 1. PostgreSQL

**Why.** The clinic database was a SQLite file on the pod's network volume: every query ~24 ms, every commit ~150 ms, one writer at a time, readers blocked during a commit, no replication or point-in-time backup.

**What.** PostgreSQL 16 (PostgreSQL licence: free, commercial use allowed) installed on the pod, one cluster listening on `127.0.0.1:5432`, database `clinic`, role `clinic` (password in `/workspace/.pg_clinic_password`, mode 600). `deploy/postgres/`:

| Script | Job |
|---|---|
| `setup_postgres.sh` | Idempotent install + configuration (WAL archiving on, `archive_timeout` 60 s, `synchronous_commit` on), role and database. |
| `backup_postgres.sh` | Base backup (`pg_basebackup`, usable on its own) + `pg_dump` into `/workspace/pg_base`, newest 8 kept; archived log older than the oldest kept backup is removed. Run every 6 h by the watchdog. |
| `restore_postgres.sh` | After a pod restart (local disk wiped): rebuilds the cluster from the newest base backup and replays `/workspace/pg_archive`. Called by `bootstrap_pod.sh` before `setup_postgres.sh`. |
| `cutover_to_postgres.sh` | The one-time switch: stops the watchdog and the API, takes a final SQLite snapshot, copies it (`tools/migrate_sqlite_to_postgres.py`), requires every table's row count to match, creates `/workspace/.use_postgres`, starts the API, restarts the watchdog; any problem falls back to SQLite untouched. |

**Where the data lives.** Not on `/workspace` (a network volume cannot hold a Postgres data directory, see `clinic-api/db.py`) but on the pod's local disk, which is wiped when the WHOLE pod restarts. Everything needed to rebuild it is on `/workspace`: the base backups and the continuously archived write-ahead log. After a pod wipe at most the last ~60 s of commits can be missing. Proven: a base backup restored into a scratch cluster gave the same row counts as the live database (38 appointments, 1,395 call records); `pg_stat_archiver` shows 44 segments archived, 0 failures.

**Switch.** The clinic API starts on PostgreSQL when `/workspace/.use_postgres` exists (`/workspace/bin/_run_clinic.sh`, generated by `deploy/start_all.sh`, sets `DATABASE_URL` from it). **Rollback:** delete that file and restart the clinic API: it reads the SQLite file again. The SQLite file is frozen at the moment of the cutover (snapshot kept in `/workspace/backups/clinic-cutover-*.db`); there is no reverse copy tool, so a rollback loses what was recorded since.

**Code changes this needed (found by running the real start-up and test suite on PostgreSQL):**
* `clinic-api/main.py`: the start-up held a read transaction and then dropped tables on another connection, which PostgreSQL makes wait for ever (SQLite let it pass) — the read transaction is ended first.
* `clinic-api/booking_log.py`: the reporting view uses SQLite functions (`strftime`, `GROUP_CONCAT`); the one SQL definition is translated for PostgreSQL (`EXTRACT(DOW …)`, `STRING_AGG`), and the session is rolled back after a logging error.
* `tools/migrate_sqlite_to_postgres.py`: drops views before tables (`--replace`).
* `tests/_clinic_app.py`: `PG_TEST_ADMIN_URL=postgresql+psycopg2://clinic:PW@127.0.0.1:5432/postgres` runs the same clinic tests against PostgreSQL, one throwaway database per test.

**Validation (all on the pod):**
* The real data copied to a rehearsal database: all 46 tables matched.
* 797 read requests (every doctor, name form and date; test price/prep in three languages; FAQ; routing; department lists; the bulk call) gave IDENTICAL answers from the live SQLite API and the PostgreSQL API.
* 20 database-facing test files: SQLite 418 passed / 9 failed, PostgreSQL 416 passed / 11 failed. The 9 are the same on both (they fail on SQLite too). The 2 extra are SQLite-only by construction: one runs `tools/booking_log.py`, a command-line viewer that opens the SQLite file; the other inspects a table with SQLite's `PRAGMA`.
* After the switch: the same Idempotency-Key sent by 24 clients at once created exactly one row in each of 6 rounds; 3 API workers are safe on PostgreSQL.

**Measured, SQLite (network volume) → PostgreSQL (local disk), same pod, 3 workers:**

| | SQLite | PostgreSQL |
|---|---|---|
| 30 reads at once, median | 339 ms | 96 ms |
| 90 reads at once, median | 723 ms | 207 ms |
| 200 reads at once, median / slowest | 1,230 / 1,978 ms | 459 / 853 ms |
| one committed write | ~150 ms | 11 ms |

Known gap: `tools/booking_log.py` (command-line viewer of the booking log) still reads the SQLite file only; the booking CSV and the `booking_log` view in PostgreSQL are unaffected.

## 2. Static answers (`agent/tools_client.py`, `main._answer_warm_loop`)

Test prices, test preparation and FAQ answers are loaded when the agent starts and once a day at `STATIC_RELOAD_HOUR` (default 5, clinic time), and answered from memory in between: no clinic API call per question, no expiry. A name the load did not cover is fetched once and then kept; a "not found" answer is never kept. A price changed during the day shows at the next load, or at once after `touch /workspace/reload_static_cache` (checked every 30 s). The spoken audio of the answers is rendered in the same pass.

## 3. The call log as one record per call (`agent/call_journal.py`, `agent/call_record.py`, `tools/call_log_archiver.py`)

* **During a call** nothing goes to the clinic API. Each event is queued to ONE writer thread that appends it to a small per-call file (`/workspace/call_journal/inflight/<call_id>.jsonl`): a local append, nothing the caller's turn waits for, and it survives a killed process.
* **When the call ends** the writer thread writes ONE line for the whole call to the day's journal (`YYYY-MM-DD.jsonl`, one fsync) and removes the in-flight file. Per call, memory is a few KB; no Redis is needed because the file is the durable queue.
* **At 01:00 clinic time** the watchdog runs `tools/call_log_archiver.py`: one process, one call at a time (`POST /api/v1/calls/{id}/events/batch`, one commit per call, idempotent by event sequence), then a CSV summary (phone as its last four digits only) and the gzip of the journal into `/workspace/call_archive/<yyyy>/<mm>/`, the gzip read back and counted, and only then the journal deleted. A call the database refused stays in the journal for the next night. A call that died with its process (in-flight file older than 6 h, no end event) is closed with the outcome `dropped`.
* **Verified live:** a call produced 0 requests to the clinic API, one journal line holding its 8 events, an empty in-flight folder; the archiver loaded it (the database returned the call record), wrote the CSV and the archive, and deleted the journal.
* **Switch:** `CALL_LOG_MODE=live` sends events to the clinic API as the call goes (with the batch endpoint, held at most 2 s; completed actions, escalations and the end go at once). Default is `journal`.
* **What this changes for staff:** today's call records (history, summaries, the audit lines written for a call's actions) appear in the database after 01:00, not at once. Bookings, holds and payments are written at once by their own endpoints.

## 4. Not done

* A reverse (PostgreSQL → SQLite) copy tool.
* A Postgres-aware `tools/booking_log.py`.
* Moving the database to a managed server in another place (the local-disk cluster is single-node; its safety net is the backup + archived log above).
